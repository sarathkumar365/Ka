# Ka UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A web UI for Ka (chat with approval cards, pending review, activity log, settings) served by a small FastAPI backend, installable on iOS as a PWA.

**Architecture:** `server/api/<feature>.py` exposes the existing core (agent loop, Db, pending queue, writer) over HTTP. Chat streams loop events over SSE; write approvals are a round trip through an in-process broker (the loop thread blocks until the browser answers). `ui/` is React + TypeScript + Vite, styled from the owner's design. `ka serve` serves API and built UI from one process on localhost.

**Tech Stack:** FastAPI, uvicorn (Python); React, TypeScript, Vite, Tailwind, React Router, TanStack Query, `@microsoft/fetch-event-source`, `react-markdown` + `remark-gfm`, `vite-plugin-pwa`, vitest.

**Spec:** `context/decisions.md` (sections "UI build rule", "UI routes", "Adaptive views"). Design: `Design/Ka.html` (local only, git-ignored). The unpacked app screens are in `Design/extracted/app.html` (a template with `{{placeholders}}`; read it for layout, copy and the `renderVals` script for state phases). The phone layout is page 3 of the same bundle.

## Global Constraints

- Scope (owner's answers): chat, pending, activity, settings. **No onboarding screen.** Settings is read-only except the theme toggle. Responsive web plus iOS PWA; no native app.
- No auth. Server binds `127.0.0.1` and rejects other `Host` headers unless listed in `config.yaml` `ui_hosts`. Phone access later via `tailscale serve` (HTTPS, tailnet only); never bind `0.0.0.0` in code.
- Public repo: no personal data, no real statements, no sample data copied from the design (store names, amounts) into code, tests or fixtures. Never commit `Design/`.
- Feature flag: `ka serve` runs only when `flags.web_ui` is true in `config.yaml` (default false in `config.example.yaml`). Remove the flag when stable.
- No change to `server/agent/loop.py`, tools or adapters. The UI consumes `Event` and `PendingWrite` as they are. Answers arrive whole; the UI types them out (skipped under `prefers-reduced-motion`).
- Views like `show_view` are v1.2: render model answers as Markdown (tables included), nothing more.
- Money shown in monospace; light and dark from CSS variables. Design tokens (dark / light): `--bg #1B1C1F / #F6F6F7`, `--surf #222327 / #FFFFFF`, `--surf2 #2B2C31 / #ECECEF`, `--t1 #E7E8EB / #1D1E21`, `--t2 #A9ACB3 / #55585F`, `--t3 #8D9098 / #6A6D75`, `--lapis #6384F0 / #2F4FC4`, `--lapis-btn #4263D9 / #2F4FC4`, `--lapis-hi #A9BDFF / #2F4FC4`, `--lapis-wash rgba(99,132,240,.14) / rgba(47,79,196,.1)`, `--sage #8FB59A / #3F6B4D`, `--line rgba(255,255,255,.09) / rgba(0,0,0,.1)`, `--S cubic-bezier(.3,1.3,.5,1)`, font Inter 400/500. Theme default is dark (the design's choice), stored choice in `localStorage` wins.
- Tests stay minimal: one per risky behaviour. UI visuals are checked in the browser pane against the design, not by snapshot tests.
- Commits: the commit guard hook gates `git commit`; touch `.claude/.reviewed` only after the owner says yes. No `Co-Authored-By` or Claude trailers. Author stays the configured noreply identity.
- Folder rule: `ui/src/features/<feature>` ↔ `server/api/<feature>.py` ↔ `context/flows/<feature>.md`.

## Review Focus

1. Browser closes or reloads while an approval is open → the loop thread must not hang; the approval auto-declines after a timeout and nothing is written (T3 test).
2. Approval answered twice (double click, two tabs) → second call gets 404 and the change is applied once (T3 test).
3. Request with a foreign `Host` header → 400, so a web page cannot drive Ka via DNS rebinding (T2 test).
4. Provider failure mid-turn (no credits, timeout) → SSE `error` event with the readable message, conversation still saved and usable (T3 test).
5. Model or tool output containing HTML, scripts or `javascript:` links → rendered as inert text (T7 test).

### Task 3: Chat streaming and approval broker

**Files:**
- Create: `server/api/approvals.py`, `server/api/chat.py`
- Modify: `server/api/app.py` (include chat router)
- Test: `tests/api/test_chat.py`

**Interfaces:**
- Consumes: `run_turn(...)`, `Event`, `PendingWrite`, `FakeAdapter`, `AdapterError`, T1 `describe_call`, `Db.add_activity`.
- Produces:
  - `ApprovalBroker`: `request(summary: str, diff: str) -> str` (new id), `wait(approval_id: str, timeout: float) -> bool` (False on timeout), `resolve(approval_id: str, approve: bool) -> bool` (False when unknown or already resolved).
  - `POST /api/chat` body `{conversation_id: str | null, text: str}` → `text/event-stream`. Frames are `event: <name>\ndata: <json>\n\n`. Names: `conversation` `{id}` (first), `tool_call` `{name, args}`, `tool_result` `{name, result}`, `approval` `{approval_id, summary, diff}`, `answer` `{text}`, `stopped` `{text}`, `error` `{message}`, `done` `{}` (last). 404 for an unknown `conversation_id`; 409 while that conversation already has a running turn.
  - `POST /api/approvals/{approval_id}` body `{approve: bool}` → `{ok: true}`; 404 when `resolve` returns False.
  - Behaviour: the turn runs in a worker thread with its own `Db`; its `approve` callback = `broker.request` then `broker.wait(timeout)`; `on_event` feeds a queue the response generator drains. When the generator is closed (client gone), set a cancelled flag so a waiting approval returns False. Each `tool_result` also records an activity row via `describe_call`; a declined or failed write records `kind="change"` with the outcome. `AdapterError` text goes out as an `error` event; any other exception becomes `{"message": "Something went wrong."}` with the type logged server-side only.

  - `test_second_turn_on_running_conversation_is_409`.
