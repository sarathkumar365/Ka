# Ka Steps 1 to 3 (Repos, Data Files, Statement Parser) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Two local git repos, validated YAML data files, and a Scotiabank chequing parser that turns a PDF into reconciled, tagged rows stored locally after a yes.

**Architecture:** A `server` Python package organised by feature. Personal data is YAML in a separate data repo, loaded through Pydantic models. The finance path is a pipeline of pure stages (parse, reconcile, tag, net) feeding a `FinanceStore` interface whose first backend is CSV files. No model calls anywhere in this plan.

**Tech Stack:** Python 3.13, uv, Pydantic v2, ruamel.yaml, pdfplumber, pytest, ruff, reportlab (dev only, builds test PDFs), argparse.

**Spec:** `Docs/2026-11-16-steps-1-3-design.md` (addendum, wins on conflict) and the full spec, which Task 2 moves to `~/Projects/ka-data/docs/ka-design.md`. Until Task 2 it is at `Docs/Ka design .md`.

## Global Constraints

- Code repo is `<code-repo>`. Data repo is `~/Projects/ka-data`. No remotes, no pushes.
- No personal data, real statement, `.env` or secret in the code repo. This plan itself contains none: real values (account numbers, names) are read from the real statement or the spec at execution time and written only into the data repo.
- No LLM call in any code in this plan.
- Money is `decimal.Decimal` end to end. Never `float`. Stored amounts are signed: negative is money out.
- All Pydantic models use `model_config = ConfigDict(extra="forbid")`.
- Dates in YAML are `YYYY-MM` or `YYYY-MM-DD` strings. IDs are never reused.
- Every behaviour change ships with a test that fails without it. Run `uv run pytest` and `uv run ruff check .` before each commit.
- Commits: one logical change, conventional prefix (`feat`, `fix`, `test`, `docs`, `chore`), ending with the line `Co-Authored-By: Claude Fable 5.2 <noreply@anthropic.com>`.
- No `ui/` folder. No Google code. No pending queue (SQLite arrives in step 6).
- Reading the real statement's values is allowed only to measure layout and to seed the data repo. Test fixtures use invented people, merchants and amounts.

## Review Focus

1. A PDF with no text layer, or from another bank: `ka import` prints one clear line and exits non-zero, no traceback. (Task 7)
2. A description containing commas or quotes survives the CSV round trip unchanged. (Task 10)
3. A row whose main line is the last line of a page and whose description is the first line of the next page keeps its description. (Task 7)
4. An import interrupted between the two CSV writes can be re-run: it finishes without duplicate rows. (Task 10)
5. Two identical charges (same day, description, amount) followed by one error correction: exactly one charge is linked, and each original is linked at most once. (Task 9)

- Binary content that does not decode as UTF-8 is checked for `pdf` and `env_file` only.
- Denylist file missing: `main` prints a warning to stderr and continues with an empty list. `detail` never echoes the matched denylist string; it gives the line number.

### Task 6: Synthetic statement PDF builder

**Files:**
- Create: `tests/fixtures/statement_pdf.py`
- Test: `tests/fixtures/test_statement_pdf.py`

**Interfaces:**
- Produces:

```python
@dataclass
class SpecRow:
    date: date
    type_text: str
    description: str | None
    amount: Decimal                      # signed, negative is money out
    column: Literal["withdrawn", "deposited"] | None = None   # None: derived from sign
    balance: Decimal | None = None       # None: computed

@dataclass
class StatementSpec:
    account_number: str = "111112222233"
    period_start: date = date(2031, 3, 24)
    period_end: date = date(2031, 4, 23)
    opening_balance: Decimal = Decimal("500.00")
    rows: list[SpecRow] = field(default_factory=list)
    rows_per_page: int = 20
    scotiabank: bool = True              # False: omit the bank markers
    text_layer: bool = True              # False: draw a rectangle only, no text
    totals: tuple[Decimal, Decimal] | None = None   # (withdrawals, deposits) override
    closing_balance: Decimal | None = None          # override

def build_statement(path: Path, spec: StatementSpec) -> None
```

Layout the builder reproduces (measured from the real statement, US Letter 612 x 792 pt, coordinates in pdfplumber terms, x from the left):
- Page 1 top right: the line `Your account number:` and, on the next line, the account number in groups `5 5 2` separated by spaces. Lower left `www.scotiabank.com` is present only when `scotiabank` is true.
- Page 1 summary, one per line, amount right-aligned with `$`: `Opening Balance on <Month D, YYYY>`, `Minus total withdrawals`, `Plus total deposits`, `Closing Balance on <Month D, YYYY>`.
- Section title: `Here's what happened in your account this statement period` (page 1) or `... in your account (continued)` (later pages), then the header row `Date  Transactions  Amounts withdrawn ($)  Amounts deposited ($)  Balance ($)`.
- Pages after the first start with the holder name, the package line and `<Month D> to <Month D, YYYY>` followed by the account number.
- Row main line: date as `Mon D` at x=73; type text at x=113; amount right-aligned at x=306 (withdrawn) or x=371 (deposited); balance right-aligned at x=436, negative shown as `-35.45`. Amounts use thousands commas.
- Description line 9 pt below the main line at x=113. Row pitch 27 pt (18 pt when there is no description).
- First table row is `Opening Balance` with only a balance. Last is `Closing Balance` with `$`.

Parsing rules:
- `pdfplumber` words with `x_tolerance=1.5`. Group words into lines by `top` within 2 pt.
- No chars on any page: `StatementFormatError("no text layer: scanned statements are not supported")`.
- Page 1 text must contain `scotiabank.com` and `Here's what happened in your account`, else `StatementFormatError("not a Scotiabank chequing statement")`.
- Named constants: `DATE_X = (70, 110)`, `TEXT_X = (110, 250)`, `WITHDRAWN_X1 = (250, 315)`, `DEPOSITED_X1 = (315, 380)`, `BALANCE_X1 = (380, 445)`. Amount columns are decided by the word's right edge `x1`.
- On each page the table starts after the line beginning `Date Transactions` and ends at the first line that is `continued on next page`, starts with `Page `, or is the `Closing Balance` row. Words with `x0 >= 450` or outside the table are dropped.
- A line with a month abbreviation and day in `DATE_X` starts a row. `Opening Balance` and `Closing Balance` rows are not transactions. A line with no word in `DATE_X` whose first word starts in `TEXT_X` is the description of the row before it, including when that row is on the previous page; all its words with `x0 < 450` are joined with spaces (descriptions can run past x=250). A second such line is appended with a space. On a row line, the type text is the words starting in `TEXT_X` that are not the amount or balance.
- A row line must have exactly one amount (withdrawn or deposited) and one balance, else `StatementFormatError` naming the page and the line text.
- Money text: strip `$` and commas, leading `-` allowed, exactly two decimals, parsed with `Decimal`.
- Summary values come from the four page-1 lines and the account number line (spaces removed). A missing one raises `StatementFormatError` naming it.

### Task 8: Reconciliation

**Files:**
- Create: `server/finance/reconcile.py`; modify `server/finance/models.py`
- Test: `tests/finance/test_reconcile.py`

**Interfaces:**
- Consumes: `ParsedStatement`, `RawRow`.
- Produces, in `models.py`: `LedgerRow(row_number: int, date: date, type_text: str, description: str, amount: Decimal (signed), balance: Decimal)`; `CheckFailure(check: Literal["row_balance","summary_totals","opening_closing","column_direction","date_out_of_period"], row_number: int | None, message: str)`. Rules:

- Date: the year from `period_start.year` or `period_end.year` that puts `(month, day)` inside `[period_start, period_end]`; none fits gives a `date_out_of_period` failure.

**Files:**

**Interfaces:**

- Produces, in `models.py`: `Transaction(id: str, account: str, statement_id: str, date: date, type: str, description: str, amount: Decimal, balance: Decimal, tag: Tag, category: str, linked_id: str)` (`category` and `linked_id` are `""` when empty). In `tagging.py`:

```python
@dataclass
class TagResult:
    transactions: list[Transaction]
    unknown_types: list[str]       # distinct type texts that used the fallback
    unknown_merchants: list[str]   # distinct descriptions with no category, own-account rows excluded
    unlinked: list[str]            # ids of netting rows with no match

def tag_rows(rows: list[LedgerRow], statement_id: str, account_id: str,
             data: KaData, existing: list[Transaction]) -> TagResult
```

Rules:
- `id = f"{statement_id}-{row_number:03d}"`.
- Text comparison everywhere: case folded, all whitespace removed.
- `load_type_rules`: code defaults for the bank, then data repo entries for the same bank replace a default with the same `type_text` or are appended.
- Tag, first match wins: (0) the row's type rule has `nets_against_original`: use that rule's tag (`refund` or `nsf_return`), so a returned loan or card payment is never counted as new borrowing; (1) description contains a `match` of an account with `mine: true`: kind `chequing`, `savings`, `investment` gives `own_transfer`; kind `credit`, `loan` gives `debt_payment` when `amount < 0` and `borrowing` when `amount > 0`; (2) type rule whose `type_text` equals the row's type; (3) fallback `purchase` if `amount < 0` else `income`, and the type text goes into `unknown_types`.
- Category: first merchant rule (file order) whose `match` is contained in the description; else `""`. Rows tagged in step (1) get no category and are not reported as unknown merchants. Rows with tag `fee`, `income`, `borrowing`, `debt_payment` are not reported as unknown merchants either.
- Netting: for each row whose type rule has `nets_against_original`, search candidates in `existing + rows before it in this statement`: same normalised description, `amount == -row.amount`, date within 60 days before or equal, not already the target of a link (a row is a target when any row in `existing` or this statement has its id as `linked_id`). Pick the latest by `(date, id)`. The link is one-way: only the netting row carries `linked_id`; the original row is never modified, so the store stays append-only. No candidate: `linked_id` stays `""`, id goes into `unlinked`.
- A merchant rule applies to any row not tagged by an own-account match, whatever its direction. E-transfers are recognised by their description (the statement prints the e-transfer marker there, with type text `Withdrawal` or `Deposit`), so the seeded merchant rule categorises both directions.
